Integrated Production Logistics Lab – Summary Architecture

Goal: unify heterogeneous devices (UR robot via sockets/TCP, mobile robots via APIs, 3D cameras/RTLS/sensors, etc.) into a single, observable and extensible stack that supports real-time monitoring, control, and logging.

1) Key concepts (layered)

  • TCP/IP: network foundation (IP addressing + packet delivery). low-level
  • Sockets: programming interface for network or local IPC (TCP/UDP sockets, Unix domain sockets). transport access
  • RESTful API: HTTP-based interface following REST constraints (resources + methods like GET/POST). application-level
  • MQTT: lightweight pub/sub messaging protocol (IoT-friendly; broker-based). edge/IoT
  • Kafka: distributed commit log + streaming platform (high throughput; retention; multiple consumers). stream backbone
  • Node-RED: orchestration / wiring tool for flows (integration glue, quick prototyping, light transforms). integration
  • ROS: robotics middleware + ecosystem (drivers, message bus, time sync, TF, toolchains). robot/sensor control & processing
  • Unity (Digital Twin): visualization + interaction layer (subscribe to real-time streams + query stored history). UI/DT

2) Recommended architecture (hybrid, keep Kafka backbone)

Principle: keep heavy streaming/logging on Kafka; keep orchestration in Node-RED; use ROS where “control + robotics math” matters.

3) Where to place ROS (rule of thumb)

  • Use ROS when the device needs control + tight robotics context: motion, timing, frames (TF), calibration, coordinate transforms, perception-to-action pipelines (e.g., point cloud → grasp pose → UR motion).
  • Skip ROS for “data-only” devices where you just stream telemetry: publish straight to Kafka (or via Node-RED) to reduce latency and complexity.
  • Hybrid is normal: a single lab can mix ROS-managed pipelines (control) and non-ROS pipelines (telemetry).

4) Where to compute point-cloud logic

  • Point cloud processing (centroid, segmentation, pose estimation) → do it in ROS (PCL ecosystem, TF, calibration, robotics-friendly math).
  • Node-RED → keep for routing, basic validation, triggering, and integration (not heavy 3D math).
  • Send to Kafka → publish results (object pose, confidence, timestamp, frame_id) rather than full dense clouds unless necessary.

5) Logging strategy (Kafka vs DB)

  • Kafka stores messages as a retained log (not deleted when consumed). Deletion depends on retention policy (time/size/compaction).
  • To keep logs long-term, add a Kafka consumer that writes into DB/Data Lake (or ELK/OpenSearch, etc.).
  • Keep real-time path lean: log by tapping the stream (consumer) rather than inserting heavy DB writes inline.

6) Unity connectivity

  • Preferred: Unity subscribes to Kafka (or a gateway consuming Kafka) for live state + queries DB for history.
  • Unity ↔ Node-RED can be used for command UI and workflows (safety checks, interlocks, authorization) before passing commands to ROS/robots.
  • Avoid putting Unity “inside” ROS unless you need ROS-native visualization tooling; keep Unity as a client.

7) Practical topic/message design

  • Kafka topics: lab.robot.state, lab.perception.targets, lab.events, lab.logs
  • Message keys: robot_id / cell_id to keep ordering per asset.
  • Schema: JSON/Avro/Protobuf + versioning; always include timestamps and frame references for perception results.

8) One-sentence takeaway

Keep Kafka as the lab-wide real-time/log backbone, use Node-RED for orchestration/integration, and introduce ROS specifically where devices require control + robotics computations (e.g., 3D camera → grasp pose → UR motion), while Unity stays as a consuming/commanding digital-twin client.
